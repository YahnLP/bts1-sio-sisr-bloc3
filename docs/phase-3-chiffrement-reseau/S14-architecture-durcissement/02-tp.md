# TP – Segmenter un réseau, filtrer et durcir un serveur Linux

*BTS SIO SISR 1re année – Bloc 3 – S14*

> [!NOTE]
> **But.** Situation : Comment organiser un réseau et configurer un serveur pour qu'une intrusion soit difficile, et ses conséquences limitées ?
>
> **Comment ce TP fonctionne.** Avant de manipuler, tu écris ce que tu **anticipes** (« J'anticipe »). Puis tu testes et tu notes ce que tu **constates**. Tu **comprends** ce que fait chaque commande (« Je comprends »). Un **bilan de compétences** clôt la séance. Les manipulations se font sur des **machines virtuelles de laboratoire**, isolées du réseau de l'établissement. Les identifiants communs d'un TP sont des **identifiants de laboratoire** : ils ne se réutilisent jamais ailleurs.

## Objectif

Concevoir l'architecture réseau sécurisée d'une PME avec sa matrice de flux, puis durcir un serveur Linux en mesurant l'effet de chaque étape.

## Contraintes

- Binôme, durée : 3 h 20.
- Partie A : sur papier ou avec un éditeur de schémas. Parties B et C : deux VM Debian de laboratoire (`srv` à durcir, `adm` poste d'administration).
- **Risque de coupure d'accès** : garde toujours une **console** de la VM `srv` ouverte (fenêtre de la VM, pas SSH) pendant les modifications.

## Partie B. Mesurer l'état initial du serveur (30 min)

Sur la VM `srv` :

```bash
sudo apt update && sudo apt install -y lynis
ss -tlnp
systemctl list-unit-files --state=enabled --type=service | head -30
sudo lynis audit system --quick 2>&1 | tail -40
sudo grep -E "hardening_index|warning\[\]|suggestion\[\]" /var/log/lynis-report.dat | head -20
```

**Je comprends.**

| Commande | Rôle |
|---|---|
| `ss -tlnp` | Liste les ports TCP en **écoute** et le programme associé |
| `systemctl list-unit-files --state=enabled` | Services lancés au démarrage |
| `lynis audit system` | Audite la configuration (authentification, noyau, réseau, services…) |
| `hardening_index` | Score de durcissement donné par Lynis (de 0 à 100) |
| `warning[]`, `suggestion[]` | Avertissements et suggestions du rapport |

## Partie C. Durcir le serveur (100 min)

Applique les mesures **une par une**, en testant après chacune.

### C1. SSH par clés

Sur la VM `adm`, crée une clé et envoie-la à `srv` (adapte l'adresse de `srv`) :

```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_lab -C "labo-sisr"
ssh-copy-id -i ~/.ssh/id_lab.pub etudiant@192.168.56.10
ssh -i ~/.ssh/id_lab etudiant@192.168.56.10 "hostname"
```

Sur `srv`, crée `/etc/ssh/sshd_config.d/10-durcissement.conf` :

```text
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
LoginGraceTime 30
AllowUsers etudiant
X11Forwarding no
```

```bash
sudo sshd -t && echo "configuration valide"
sudo systemctl reload ssh
```

**J'anticipe.** Depuis `adm`, une connexion **sans clé** (`ssh -o PubkeyAuthentication=no etudiant@192.168.56.10`) va-t-elle réussir ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

**Non** : `Permission denied (publickey)`. Le serveur n'accepte plus le mot de passe.

</details>

```bash
ssh -o PubkeyAuthentication=no etudiant@192.168.56.10
ssh -i ~/.ssh/id_lab root@192.168.56.10
ssh -i ~/.ssh/id_lab etudiant@192.168.56.10 "echo connexion par clé OK"
```

10. Pourquoi lancer `sshd -t` **avant** `reload` ? Que risquait-on sinon ? ______________________
11. Pourquoi désactiver l'authentification par mot de passe fait-il disparaître toute une famille d'attaques (S03) ? ______________________
12. Où est stockée la clé privée sur `adm` ? Comment la protéger (phrase secrète) ? ______________________

### C2. Pare-feu local en refus par défaut

```bash
sudo apt install -y ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.56.20 to any port 22 proto tcp
sudo ufw enable
sudo ufw status verbose
```

Teste depuis `adm`, puis depuis une autre machine ou adresse :

```bash
ssh -i ~/.ssh/id_lab etudiant@192.168.56.10 "echo OK"
nc -zv 192.168.56.10 80
```

**Je comprends.**

| Commande | Rôle |
|---|---|
| `default deny incoming` | **Refus par défaut** de tout le trafic entrant |
| `default allow outgoing` | Autorise les connexions sortantes (à resserrer sur un serveur sensible) |
| `allow from … to any port 22` | N'autorise **que** le poste d'administration à joindre SSH |
| `enable` | Active les règles (après avoir ouvert l'accès SSH !) |

13. Pourquoi a-t-on ouvert le port 22 **avant** `ufw enable` ? ______________________
14. Que répond le port 80 ? Est-ce « fermé » ou « filtré » (silencieux) ? ______________________
15. Quelle règle ajouterais-tu si `srv` devait servir un site HTTPS, mais seulement au LAN `192.168.56.0/24` ? ______________________
