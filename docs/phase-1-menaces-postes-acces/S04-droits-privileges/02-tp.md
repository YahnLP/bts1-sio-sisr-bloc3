# TP – Construire une matrice de droits et l'appliquer sous Linux et Windows

*BTS SIO SISR 1re année – Bloc 3 – S04*

> [!NOTE]
> **But.** Situation : Comment donner à chacun exactement l'accès dont il a besoin, et pas un de plus ?
>
> **Comment ce TP fonctionne.** Avant de manipuler, tu écris ce que tu **anticipes** (« J'anticipe »). Puis tu testes et tu notes ce que tu **constates**. Tu **comprends** ce que fait chaque commande (« Je comprends »). Un **bilan de compétences** clôt la séance. Les manipulations se font sur des **machines virtuelles de laboratoire**, isolées du réseau de l'établissement. Les identifiants communs d'un TP sont des **identifiants de laboratoire** : ils ne se réutilisent jamais ailleurs.

## Objectif

À partir du cas InnoTech, construire une matrice de droits justifiée, l'appliquer sous Linux avec des groupes et des ACL, vérifier les accès effectifs, puis repérer et corriger un droit excessif sous Windows.

## Contraintes

- Binôme, durée : 3 h 15. VM Debian et VM Windows de laboratoire.
- Les accès se donnent **par des groupes**, jamais directement à une personne.
- Tout écart entre la matrice et la réalité se **documente**.

## Partie B. Appliquer la matrice sous Linux (60 min)

On met en œuvre un sous-ensemble : `Clients`, `Compta`, `RH` et `Direction`, avec quatre utilisateurs de laboratoire (créés sans mot de passe : on les utilise avec `sudo -u`).

```bash
sudo apt install acl
sudo groupadd g_commercial; sudo groupadd g_compta; sudo groupadd g_rh; sudo groupadd g_direction
sudo useradd -m -s /bin/bash -G g_commercial sophie
sudo useradd -m -s /bin/bash -G g_compta marc
sudo useradd -m -s /bin/bash -G g_rh julie
sudo useradd -m -s /bin/bash -G g_direction paul
sudo mkdir -p /srv/data/clients /srv/data/compta /srv/data/rh /srv/data/direction
```

**Je comprends.**

| Commande | Ce qu'elle fait |
|---|---|
| `groupadd g_...` | Crée un groupe : c'est le **rôle** (RBAC) |
| `useradd -m -s /bin/bash -G g_x nom` | Crée un utilisateur avec son dossier personnel et **l'ajoute au groupe** `g_x` |
| `mkdir -p /srv/data/...` | Crée les dossiers de données du serveur de fichiers |

Applique ensuite les droits de base (un groupe propriétaire par dossier, accès réservé au groupe) :

```bash
sudo chgrp g_commercial /srv/data/clients; sudo chmod 2770 /srv/data/clients
sudo chgrp g_compta     /srv/data/compta;  sudo chmod 2770 /srv/data/compta
sudo chgrp g_rh         /srv/data/rh;      sudo chmod 2770 /srv/data/rh
sudo chgrp g_direction  /srv/data/direction; sudo chmod 2770 /srv/data/direction
```

**Je comprends.** `chgrp` change le **groupe propriétaire** du dossier. `chmod 2770` donne `rwx` au propriétaire et au groupe, **rien aux autres** (le dernier `0`), et le **`2`** active le bit **setgid** : un fichier créé dans le dossier hérite du **groupe du dossier** au lieu du groupe principal de son auteur.

**J'anticipe.** Après ces commandes, `marc` (g_compta) peut-il lire `/srv/data/clients` ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

**Non** : `marc` n'est pas dans `g_commercial` et les « autres » n'ont aucun droit (`770`). Il faut un droit **supplémentaire** pour la comptabilité : c'est le rôle des ACL ci-dessous.

</details>

La comptabilité doit **consulter** `Clients` (facturation). On ajoute un droit de lecture par **ACL**, y compris pour les fichiers futurs :

```bash
sudo setfacl -m g:g_compta:rx /srv/data/clients
sudo setfacl -d -m g:g_compta:rx /srv/data/clients
getfacl /srv/data/clients
```

**Je comprends.** `setfacl -m g:g_compta:rx` ajoute une entrée pour le **groupe** `g_compta` : lecture et traversée (`rx`). L'option `-d` définit l'ACL **par défaut** appliquée aux fichiers créés ensuite.

Teste maintenant les accès avec chaque utilisateur et remplis le tableau.

```bash
sudo -u sophie touch /srv/data/clients/devis1.txt
sudo -u sophie ls /srv/data/rh
sudo -u marc ls /srv/data/clients
sudo -u marc touch /srv/data/clients/essai.txt
sudo -u julie ls /srv/data/compta
sudo -u paul ls /srv/data/direction
```

| Utilisateur | Action | Résultat attendu | Résultat observé |
|---|---|---|---|
| sophie | Créer un fichier dans `clients` | | |
| sophie | Lister `rh` | | |
| marc | Lister `clients` | | |
| marc | Créer un fichier dans `clients` | | |
| julie | Lister `compta` | | |
| paul | Lister `direction` | | |

**Questions.**

1. Un des tests ne donne pas le résultat attendu d'après ta matrice : lequel, et pourquoi ? Corrige-le avec une ACL. ______________________
2. À quoi sert `id marc` ? Qu'indique `sudo -l -U marc` ? ______________________
3. Pourquoi a-t-on utilisé `sudo -u` pour tester, plutôt que de se connecter en `root` ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

2. `id marc` liste les **groupes** de l'utilisateur ; `sudo -l -U marc` liste les **commandes `sudo` autorisées** pour lui (par défaut, aucune).
3. `root` **contourne** les permissions : un test fait en `root` réussit toujours et ne prouve rien. On teste **avec l'identité de l'utilisateur concerné**.

</details>

### Traiter un départ

Marc quitte l'entreprise vendredi. Désactive son compte **sans le supprimer**, puis contrôle :

```bash
sudo usermod -L -e 1 marc
sudo passwd -S marc
sudo chage -l marc
```

**Je comprends.** `-L` verrouille le mot de passe ; `-e 1` fixe la date d'expiration du compte au 2 janvier 1970, donc **expiré** ; `passwd -S` indique l'état (`L` pour verrouillé) ; `chage -l` affiche les dates de validité.

**Question.** Pourquoi ne supprime-t-on pas tout de suite le compte et ses fichiers ? Qui doit récupérer les fichiers de Marc ? ______________________

## Partie C. Auditer des droits sous Windows (45 min)

Sur la VM Windows (PowerShell en administrateur) :

```powershell
New-Item -ItemType Directory -Path C:\Data\RH -Force
icacls C:\Data\RH /grant "*S-1-1-0:(OI)(CI)F"
icacls C:\Data\RH
```

**Je comprends.** `*S-1-1-0` est l'identifiant (SID) du groupe **« Tout le monde »**, valable quelle que soit la langue de Windows. `(OI)(CI)` fait hériter les fichiers et sous-dossiers ; `F` signifie *contrôle total*.

**J'anticipe.** Un salarié du service commercial peut-il maintenant lire et modifier les données RH ? ______________________

Tu viens de **créer un écart** : corrige-le en construisant l'accès par groupe.

```powershell
net localgroup G_RH /add
icacls C:\Data\RH /inheritance:r
icacls C:\Data\RH /grant "BUILTIN\Administrators:(OI)(CI)F" "NT AUTHORITY\SYSTEM:(OI)(CI)F" "G_RH:(OI)(CI)M"
icacls C:\Data\RH
```

**Je comprends.** `/inheritance:r` **retire les droits hérités** du dossier parent ; on redonne ensuite uniquement ce qui est nécessaire : administrateurs et système (pour l'exploitation), et le groupe `G_RH` en **modification** (`M`).

**Questions.**

1. L'entrée « Tout le monde » a-t-elle disparu après ces commandes ? Pourquoi ? Quelle commande faut-il ajouter pour la retirer ? ______________________
2. Retire-t-on les droits des administrateurs ? Pourquoi les avoir laissés ? Que signifie « modification » (`M`) par rapport au « contrôle total » (`F`) ? ______________________
3. Quelle est la différence, pour la sécurité, entre accorder `M` à un **groupe** et à un **utilisateur** ? ______________________
